# MEASURED UNDER NODE, NOT wasmkit, and the distinction is not academic. #2894 ran one module file
# byte for byte under both: an OCCT exception thrown several frames below the bridge's `catch (...)`
# is caught under Node and reaches `std::terminate` under wasmkit 0.3.1. Three entries that used to
# be on this list, and four file exclusions plus a whole target in `Package.swift`, were that
# interpreter and not this port. They are gone. The target for #1689 is a browser, so the runner
# drives Node with the browser's own WASI shim.
#
# `Scripts/run-wasm-tests.sh` asserts the failure set is EXACTLY this list: a new failure
# fails the run, and so does a test in this list that starts passing, because a line nobody removes
# is how a fixed bug gets recorded as still broken.
#
# Format: <suite-or-test-name-as-swift-testing-prints-it>  # <issue>
#
# This is not a suppression list. Everything here is a measured cross-platform difference in shipped
# behaviour, and each line is a claim that the difference is understood and tracked, not tolerated.
#
# The identifier is matched against the text Swift Testing prints after `✘ Test `, up to the first
# ` recorded an issue` or ` failed after`. Quote-wrapped display names are matched with their quotes.

# --- exact-equality baselines do not survive a different libm --------------------------------
# `Issue791ConvertCircleHelperTests` (Geom2d, 2 tests) and `Issue791ConvertSphereHelperTests`
# (Surface, 2 tests) each compare a computed pole against a hardcoded baseline with `==`,
# not a tolerance. The wasm build links WASILibc's math functions and the Apple build links Darwin's,
# and IEEE 754 does not pin the results of transcendentals to the last bit, so `sin`/`cos` on the two
# platforms legitimately differ in the final places and an exact comparison cannot hold across both.
#
# Nothing is wrong with the geometry here and nothing is wrong with the port. The tests are wrong to
# use `==` on a value derived through trigonometry, and the fix is a tolerance, which is a change to
# an Apple-platform test and so belongs in its own PR rather than this one. Listed rather than
# excluded because they are real failures a reader should see.
#
# `Issue196PolyHLRTests` is the same cause with a tolerance rather than an exact comparison, and it
# reached a wasm run for the first time under #2928. Its subject holds here: a coarser mesh really
# does draw fewer outline edges and more sharp ones, and both relational assertions pass, as do both
# FINE baselines (17,041 and 1,873 within 1%). The two COARSE baselines do not: measured 3,532 against
# 3,578 (-1.3%) and 2,160 against 2,089 (+3.4%). A coarse triangulation has proportionally fewer
# facets, so the same last-place libm differences move more of them, and 1% is tighter than the
# mesher's own cross-platform reproducibility at that deflection. The fix is a wider tolerance on the
# two coarse figures, which is a change to an Apple-platform test and belongs in its own PR.
"deflection is honoured, a coarser mesh draws fewer outline edges and more sharp ones"  # coarse mesh baseline vs a different libm
fullCircleOriginMatchesPriorBaseline()  # exact-equality baseline vs a different libm
offsetArcMatchesPriorBaseline()  # exact-equality baseline vs a different libm
unitOriginMatchesPriorBaseline()  # exact-equality baseline vs a different libm
offsetTiltedMatchesPriorBaseline()  # exact-equality baseline vs a different libm

# --- #2926: a live parameter goes inert on wasm -----------------------------------------------
# `nlPlateDeformedG3(constraints:tolerance:)` run at 1e-1 and at 1e-3 returns surfaces that differ by
# exactly 0.0 here, so the tolerance has no effect. It does on Apple, which is what #999 was filed to
# prove: these parameters were once declared and dropped by the bridge, and these tests exist to keep
# them live. Three readings are open and the issue names the test for each: the value not reaching
# OCCT, the solver terminating on an iteration limit either way (a different libm changes the
# arithmetic, so the iteration counts need not match Apple's), or an exception inside the solver being
# swallowed differently (#2894). Only the first and third would make it a defect.
#
# Listed and not excluded, because it is a wrong answer rather than a trap: the suite reports it and
# carries on, which is what this list is for.
"Varying the tolerance changes the G3 result"  # 2926

# --- #2929: BRepCheck does not fault a cleared SameParameter flag ------------------------------
# `BRepLibExtendedTests."Same parameter all"` clears edge 0's SameParameter flag on a box and expects
# BRepCheck to fault it. On Apple it does; here the box still reads valid, so the assertion that
# fails is the one proving the fixture is genuinely broken rather than the one testing the subject.
# Without that assertion the test would pass VACUOUSLY on wasm, which is the blind-test shape #2904
# was filed to remove: the test is doing its job and the kernel behaviour underneath differs.
#
# Two causes are open and the issue names the single measurement that separates them: the flag write
# not taking effect, or BRepCheck_Analyzer not faulting the flag/geometry mismatch. The second would
# make every flag-based validity verdict on wasm suspect, and `Shape.isValid` is on the path every
# IGES export takes through `Exporter.validateExportInputs`, so it wants a sweep rather than a fix.
"Same parameter all"  # 2929

# OCCTMiscTests have run here. Eight tests pass on Apple and fail on wasm, all because the facility
# the OCCT wrapper reaches does not exist on this target and the wrapper answers rather than
# refusing. Each is measured, and #3025 holds the open question, which is a decision per row rather
# than a fix per row: document the limit on the wasm surface, fix the harness, or leave it listed.
#
# Listed and not excluded, deliberately. Every one of these is a real property of the wasm surface
# that a consumer targeting the browser needs to know, and the run asserts this set exactly, so none

# #3026: those never reach the behaviour they are named for, because the fixture is unreadable.
