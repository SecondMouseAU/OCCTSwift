# owns each. `Scripts/run-wasm-tests.sh` asserts the failure set is EXACTLY this list: a new failure
# fails the run, and so does a test in this list that starts passing, because a line nobody removes
# is how a fixed bug gets recorded as still broken.
#
# Format: <suite-or-test-name-as-swift-testing-prints-it>  # <issue>
#
# This is not a suppression list. Everything here is a measured cross-platform difference in shipped

#
# The identifier is matched against the text Swift Testing prints after `✘ Test `, up to the first
# ` recorded an issue` or ` failed after`. Quote-wrapped display names are matched with their quotes.

# --- #2891: OCCT's inline argument validation does not raise on wasm ---------------------------
# gp_Dir's zero-norm check is inline in gp_Dir.hxx and `No_Exception` is NOT defined when the bridge
# compiles for wasm (both measured), so the check should fire on both platforms. It does not.
# Measured with OCCTDiagnostics.capturing around one call, same inputs:
#   Apple: records=2, "Standard_ConstructionError: gp_Dir() - input vector has zero norm",
#          translated origin (5, 3, 2), the documented unmoved fallback.
#   wasm:  records=0, no exception at all, translated origin (6, 5, 5) -- the degenerate axis was
#          used as though it were valid.
# Both header trees are byte-identical for gp_Dir.hxx and both are 7,160 files, so this is not a
# header or macro difference. It is the exception path itself.
"OCCTAx3Create: parallel direction/xDirection overwrites sentinel outputs, not left untouched"  # 2891
"OCCTAx3MirrorPoint: degenerate input axis overwrites sentinel outputs with the input point unmoved"  # 2891
"OCCTAx3Translate: degenerate input axis overwrites sentinel outputs with the input point unmoved"  # 2891

# --- the kernel skew: wasm is one patch behind native (#2827, #2873) --------------------------

# `v4.0.0-kernel.3` repin pinned patch `0043` (the by-plane `BRepGProp_Vinert` mass) on native
# without taking the 69-minute wasm rebuild, so native carries 31 carried patches and wasm 30, and
# `Face.volumeInertia(planeNormal:planeDistance:)` still returns the fabricated 0.0 here.
#
# Until #2793 that acknowledgement was a sentence in a text file. These four lines are the same claim

# runner then fails until they are deleted from this list.

# --- exact-equality baselines do not survive a different libm --------------------------------
# `Issue791ConvertCircleHelperTests` (Geom2d) and `Issue791ConvertSphereHelperTests` (Surface) each
# compare a computed pole against a hardcoded baseline with `==`,
# not a tolerance. The wasm build links WASILibc's math functions and the Apple build links Darwin's,
# and IEEE 754 does not pin the results of transcendentals to the last bit, so `sin`/`cos` on the two
# platforms legitimately differ in the final places and an exact comparison cannot hold across both.
#
# Nothing is wrong with the geometry here and nothing is wrong with the port. The tests are wrong to
# use `==` on a value derived through trigonometry, and the fix is a tolerance, which is a change to
# an Apple-platform test and so belongs in its own PR rather than this one. Listed rather than
# excluded because they are real failures a reader should see.
fullCircleOriginMatchesPriorBaseline()  # exact-equality baseline vs a different libm
offsetArcMatchesPriorBaseline()  # exact-equality baseline vs a different libm
unitOriginMatchesPriorBaseline()  # exact-equality baseline vs a different libm
