== part 1: default-constructed objects, on deliberately poisoned heap storage ==

The three constructors set only these members:
  DimensionObject:     myHasPlane, myHasPntText, myHasConnection1, myHasConnection2
  GeomToleranceObject: myHasAxis, myHasPlane, myHasPnt, myHasPntText, myAffectedPlaneType
  DatumObject:         myIsDTarget, myIsValidDT, myHasPlane, myHasPnt, myHasPntText
Everything else below reads storage nobody wrote. Against this kernel and this allocator
every such member happens to read back as 0, which is why the defect is invisible in
ordinary use; it is still storage no constructor assigned, so the bridge's create path
sets the neutral values explicitly rather than relying on it.

== part 4: the three shapes no header states ==

  NbDescriptions=1  GetDescription(0)=first  GetDescription(1)=
  index base is 0: GetDescription(0) is the first entry and GetDescription(1) falls
  outside the array, where the accessor answers an empty string rather than throwing.

  GetDirection on an object that never had one: returned=true dir=(1,0,0)
  The bool is a constant true (XCAFDimTolObjects_DimensionObject.cxx:419-423 returns
  true unconditionally), so it cannot report absence and the vector it writes is the
  default-constructed gp_Dir rather than a stored one.

  Part 2's readback rows print the semantic name of a dimension, tolerance and datum
  nobody ever named. Each reports the GD&T table's own marker string, because
  XCAFDoc_DimTolTool::AddDimension/AddGeomTolerance/AddDatum set the label's TDataStd_Name
  to "DGT:Dimension" / "DGT:Tolerance" / "DGT:Datum", and that is the same attribute
  GetSemanticName reads. XCAFDoc_Dimension.cxx's setString helper also returns early on a
  null handle, so the name cannot be cleared once set.
