# #1403 Phase 3 re-scope, measured against untruncated logs

The classification in [`README.md`](README.md) was drawn from logs **truncated at 200 KB each**,
which is 64 of 242 race reports, and only 13 of 129 for `iges_write`. Its bucket (b) table also
mixed measured rows with inspected ones without marking which was which. This file re-derives it
from complete logs and labels every row.

## Method

Untruncated run of the five registered DE scenarios, same binary and options as
`Scripts/tsan-stress.sh run` (`8 20`, `MMGT_OPT=0`,
`TSAN_OPTIONS=halt_on_error=0:exitcode=66:suppressions=Scripts/tsan.supp`), against
`Libraries/occt-install-tsan`. **178 reports**: `step_write` 62, `mixed` 54, `iges_write` 38,
`iges_read` 14, `step_read` 10.

Classified three ways, because no single view is sufficient:

- **`Location is global '<name>'`**, which names the shared object outright. 56 reports.
- **`Location is heap block`** plus the first non-allocator frame of its allocating stack. 122 reports.
- **Frame #0** of each access, which is where the racing read or write happens.

**Counts are run-unstable and must not be quoted as defect counts.** `iges_write` was 129 in the
baseline run and 38 here, `step_write` 44 and 62, from the same binary and arguments. Rank by
*which* sites appear, never by how often.

## What changed against `README.md`'s bucket (b)

### Removed, for zero measured support

**`Interface_Protocol::theactive()`.** The strings `theactive`, `theact` and
`Interface_Protocol::` appear **nowhere in all 178 reports**. It is a genuine unsynchronised global
by inspection, and `IFSelect_WorkSession::SetProtocol` (`:106`) is its only writer in the tree, but
nothing in the DE gate reaches it concurrently. It was listed in a table otherwise presented as
measurement. Keep it as an inspection note, not a Phase 3 target.

### Confirmed, and they were right

| Row | Evidence |
|---|---|
| `errhand` | frame #0 `IFSelect_WorkSession.cxx:86`, 28, the busiest site measured |
| `STEPControl_ActorWrite::mygroup` | frame #0 `STEPControl_ActorWrite.cxx:473`, 9 |

### Added, all absent from both #1403 and `README.md`

**1. `NM_DETECTED`, and it is the highest-value target found.**
`STEPControl_ActorRead.cxx:208`, a **non-`static`** file-scope `bool`. Reset at `:993`, set at
`:1028`/`:1041` during one entity's transfer, read at `:742` and `:805` to decide whether to unwrap
a `COMPOUND` result. Two concurrent STEP reads: one thread's non-manifold detection makes another
thread take the non-manifold branch on its own compound, **silently changing the shape returned**.
That is a wrong answer reachable from concurrent `Shape.load(from:)`/`Document.loadSTEP`, not only
a race, which puts it in #280's class rather than #1403's.

Upstream has already written the fix down, at `:205`:

> Set global var to inform outer methods that current representation item is non-manifold.
> The better way is to pass this information via binder or via TopoDS_Shape itself, however,
> this is very specific info to do so...

So the relocate-to-owner direction is upstream's own stated preference, which is the strongest
position to file from.

**2. The `static int` sentinel family, which is `errhand`'s shape exactly.**
`errh` (`Interface_CheckTool.cxx:39`), `thefic`/`thenm0`/`thenp0`
(`Interface_FileReaderData.cxx:38-40`), `testconv` (`IGESData_ParamReader.cxx:34`). The
`FileReaderData` pair carries the same concession `errhand` does:

> So, we assume that we read one file at a time (reasonable assumption)

`0036` is the template for all of these, so they are cheap follow-ons rather than new design work.

**3. Three shared `NCollection_DataMap` registries.**
`listad` (`XSControl_Controller.cxx:59`), `atemp` (`Interface_InterfaceModel.cxx:44`),
`astats` (`MoniTool_TypedValue.cxx:30`). These are the source of the `TCollection_AsciiString`,
`NCollection_DataMap` and `Standard_Handle` frame-#0 noise (20+17+13+11+11+10+8 reports), which
`README.md` correctly called symptoms but attributed to the wrong owners.

## Bucket (a), and why it dominates the heap reports

94 of the 122 heap-block races are objects allocated during one-time init and raced because the
init is unguarded: `Interface_Static::Init` 38, `STEPControl_Controller` ctor 14,
`ShapeProcess::RegisterOperator` 12, `ShapeProcess_OperLibrary::Init` 9, `IGESControl_Controller`
ctor 8, `XSControl_Controller::Record` 8, `IGESControl_Controller::Init` 3, `IGESData::Init` 2.

These are bucket (a) by the plan's taxonomy, but note `IGESControl_Controller`'s constructor flag
has **no mutex at all** where `STEPControl_Controller`'s has one
(`IGESControl_Controller.cxx:76-82` vs `STEPControl_Controller.cxx:61-63`). Cheap to fix and
independent of everything else.

The remaining 28 are per-operation: `IGESSelect_WorkLibrary::ReadFile` 15,
`Interface_Check::SendMsg` 4, `IGESData_IGESModel::ClearHeader` 4,
`Interface_InterfaceModel::SetTemplate` 2, and two singletons.

## Recommended Phase 3 order

1. **`NM_DETECTED`** first. Wrong answers outrank races, and upstream has pre-written the rationale.
2. **The `static int` sentinel family**, as one patch. `0036` already proves the pattern.
3. **`IGESControl_Controller`'s unguarded init flag**, matching STEP's existing mutex.
4. **The three `DataMap` registries**, which need an ownership decision rather than a sentinel move.
5. `STEPControl_ActorWrite` and `IGESToBRep_Actor`, the actual architectural change #1403 names.

`bufstr` stays on #2054: it hands out a pointer to a shared buffer, so it needs an API decision.

## Reproducing

```bash
Scripts/tsan-stress.sh build     # once, if Libraries/occt-install-tsan is absent
Scripts/tsan-stress.sh run       # the five 1157 scenarios are registered
```

The raw logs are ~2.5 MB and are deliberately **not** committed; the tables above are the artifact.
Regenerate with the command above and re-derive by `Location is global`, `Location is heap block`
and frame #0, as described under Method.
