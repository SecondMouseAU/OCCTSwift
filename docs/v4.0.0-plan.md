# v4.0.0 Release Plan

The scope, the working method, and the order of execution for the next major release. This is the
durable reference; the GitHub issues point here rather than restating it.

Tracking issue: **#1144** (mirrors #669's role for v2.0.0). Branch: none shared, per #377's
corrected branch policy — each pass cuts its own `refactor/<issue>-pass<name>` branch from `main`'s
tip and merges straight back, no long-lived integration branch.

## Why this plan exists, and why it isn't optional

**v3.0.0 shipped 2026-08-18 without one.** It accumulated two breaking changes (#844, #943) and a
tail of Pass 2a/2b/3 dedup work, and got tagged when it was time to cut a release rather than from a
drawn scope line. That worked because it was small. It will not work again: **the next release is
already forced to be a major**, independent of anything below.

Measured against `main` at the tag, five PRs merged since v3.0.0 (8 days, as of this plan) already
state `MAJOR` SemVer impact under [`semver-at-release.md`](../okf/policies/semver-at-release.md)'s
Rule 2:

| PR | break |
|---|---|
| [#986](https://github.com/SecondMouseAU/OCCTSwift/pull/986) | `Document.commitWithDelta()` silently stops raising the undo limit |
| [#1069](https://github.com/SecondMouseAU/OCCTSwift/pull/1069) | 5 `nlPlateDeformed*` functions return a different surface for the same input, silently |
| [#1084](https://github.com/SecondMouseAU/OCCTSwift/pull/1084) | `OCCTDatumInfo`'s `name` field removed from the public C header |
| [#1096](https://github.com/SecondMouseAU/OCCTSwift/pull/1096) | `checkOuterBound` returns `Bool?`, not `Bool` |
| [#1138](https://github.com/SecondMouseAU/OCCTSwift/pull/1138) | 14 more `SAWireAnalysis` functions return `Bool?`, not `Bool` |

That count is a floor: several other PRs in the same window carried no machine-parseable `## SemVer
impact` heading and were not re-checked by hand for this table. Whatever ships next is v4.0.0
whether or not another line of this document is written. What this plan actually decides is **how
much lands in it and how long that takes**, which is a real decision with a real failure mode: see
the "why not just hold everything" discussion this plan resolves, recorded in the issue thread that
produced it.

## The rule that keeps this from becoming "hold everything, forever"

**Every pass in this programme has found more work mid-flight than it started with.** #396 spawned
#1071 spawned two more PRs. #928 spawned #930. Pass 4a's own closing comment has a section literally
titled "Added after this summary was first posted." That is not a criticism of any of those passes;
finding real, unscoped work is what an audit is for. It is why this section exists.

**A finding discovered while working an in-scope issue ships in v4.0.0 if it stays inside that
issue's own lane.** A finding that opens a materially new workstream (a new epic, a new census
family, a new spike) gets filed and explicitly deferred to whatever ships after v4.0.0, the same way
#707 and #726's Segment 3-onward were deferred here. The test is the one #396 already uses for
promoting a backlog candidate to its own issue: has the audit that touches it actually run and found
something, not "could this plausibly also need auditing."

## Beta and release-candidate plan

**`v4.0.0-beta.1` waits for a specific, named list, not a time or a lane boundary.** Milestone
[`v4.0.0-beta.1`](https://github.com/SecondMouseAU/OCCTSwift/milestone/2) holds the loose tail of
small, already-scoped chores and doc fixes sitting in Pass 4a's orbit: #781, #1010, #1047, #1052,
#1062, #1063 (no existing parent issue, sub-issue-linked directly under #1144), plus #949, #950,
#951 (orphaned under the closed Pass 3, #384), #976 (Pass 4c's, #387) and #1044 (the refman-coverage
epic's, #807). Two siblings on the same list, #1060 and #1061, already closed 2026-08-26. Beta1 does
not cut until the rest close.

**`v4.0.0-beta.2` shipped as Pass 4b (#386) alone.** Milestone
[`v4.0.0-beta.2`](https://github.com/SecondMouseAU/OCCTSwift/milestone/3), 1 issue, closed.

**The "roughly one per closed source lane" plan below did not happen in practice, stated plainly
rather than glossed over.** 4c (#387), 4d (#388), the OCAF lanes 3b/3c (#982/#983), their refman
companions (#812-#814), and #1044 all closed between beta.2 and beta.3 with **no milestone opened
for any of them**; they carry the `release:v4.0.0` label and their own sub-issue parents, but the
per-beta tracking table below's "primary membership signal" row was silently not followed for that
whole stretch. Not backfilled here retroactively, since the milestone's value is as a real-time
signpost and a milestone assembled after the fact from git history is not that.

**`v4.0.0-beta.3` is Pass 5a-5d (#389-#392), now closed, plus #1045's substrate-package partition
decision.** Milestone [`v4.0.0-beta.3`](https://github.com/SecondMouseAU/OCCTSwift/milestone/4), 56
issues (the four pass-tracking issues, their 51 total sub-issues, and #1045), 55 closed at the
milestone's creation and the 56th (#1045 itself) pending its own closing PR (#1374).

**Betas are published as GitHub pre-releases, never as the repo's latest release**, the same
mechanism already used for `v3.0.0-kernel.1`/`v2.0.0-kernel.2`. Confirm Swift Package Index's actual
handling of a `-beta.N` prerelease tag before the first one is actually cut as a release (as
opposed to the milestone bookkeeping above, which is tracking only), so it is never surfaced there
as the recommended or latest version; a correctly-formed SemVer prerelease tag should already keep
SPI from doing that, but this has not been verified against SPI's current behaviour specifically.
**None of `v4.0.0-beta.1`/`.2`/`.3` has actually been tagged or released as of this writing**; the
milestones track scope, not a cut release.

**Further betas open at natural boundaries as later lanes get scoped**, not on a fixed schedule.
Phase 6 (#819, #820, #872) is next; #820 has already absorbed #1045's fifteen substrate packages
(comment on #820), so its own scope is now wider than the issue's original text.

**RCs start once Phase 6 closes.** Exit criteria, fixed here rather than decided ad hoc when the
moment arrives:

1. Full `swift test` clean across enough runs to cross the known ~1-in-10 parallel-suite flake rate
   (#341/#344/#345's own history says this repo's suite needs more than one green run to mean
   anything).
2. `Scripts/tsan-stress.sh all` clean.
3. `gate-scripts` (all eight gates plus their `--self-test`s) clean, and the three censuses'
   `--self-test`s clean.
4. **A real downstream consumer built and tested against the RC tag, not just this repo's own
   suite.** This is not a generic best practice, it is a repeat of a specific, already-recorded
   miss: v2.0.0's own break table omitted #595 until building swiftGCS against the tag broke at two
   call sites nothing in this repo's own testing could have predicted. An RC that only exercises
   `OCCTSwift`'s own tests would not have caught it either.

Promote to `v4.0.0` once an RC meets all four with no new findings. A finding at RC stage is a new
RC, not a footnote on the release notes.

## How the release is tracked

Reintroduced here because v3.0.0 skipped it (no milestone was ever opened for it, which is part of
why it had no plan document either), and refined once during setup: v2.0.0 used one `v2.0.0`
milestone for the whole release; this one uses **one milestone per beta** instead
(`v4.0.0-beta.1`, `v4.0.0-beta.2`, more to follow), since that is the granularity actually being
decided in practice.

**Sub-issue links stay with each issue's real parent**, not the tracking issue: GitHub allows one
parent per issue, so something already under #377 or #807 cannot also formally link under #1144.
Confirmed while setting this up: #386's parent is #377, #1044's is #807, #949's is #384 (closed),
#976's is #387. #1144 formally links only the handful of standalone items that had no existing
parent (#781, #1010, #1047, #1052, #1062, #1063). The milestone, not the sub-issue tree, is the real
cross-cutting "is this in v4.0.0" signal for everything else.

| Mechanism | What it expresses |
|---|---|
| **`v4.0.0-beta.N` milestones** | Which release chunk an issue ships in. The primary membership signal. |
| **Sub-issue links, on each issue's own natural parent** | Hierarchy/workstream, unchanged from #377/#807's own trees. |
| **#1144's own sub-issue tree** | Only the standalone items with no other parent. |
| **`release:v4.0.0` label** | Membership in this major, independent of which beta. Filters where milestones are awkward. |
| **`phase:*` labels** | Workstream, already in use and listed in the Scope tables above. |
| **Board `Status`** | State: Backlog, In Progress, PR Review, Code-Review, Ready, Done. |

## Versioning

Rule 2 of [SEMVER.md](SEMVER.md): accumulated breaking changes to the public Swift API. The OCCT
kernel is not expected to move for this release (no OCCT 9.0 signal), so Rule 1 does not apply here
the way it did for v1.0.0.

Every break lands in `SEMVER.md`'s register with its migration before the tag, assembled once, at
release, per [`semver-at-release.md`](../okf/policies/semver-at-release.md), from each merged PR's
own `## SemVer impact` statement. **Do not hand-edit `SEMVER.md` before then**, the same rule that
already governs every other release.

Known breaks so far, all already merged: #844, #943 (both shipped in v3.0.0, listed here only so the
running total is legible), #970, #1049/#1046, #1055/#1056, #1058, #1074. This list will grow as
4b-4d, 3b/3c and 5a-5d run; that is expected, not a scope failure, the same way v2.0.0's own break
count grew across its execution.
