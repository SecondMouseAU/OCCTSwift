# v4.0.0 Release Plan

The scope, the working method, and the order of execution for the next major release. This is the
durable reference; the GitHub issues point here rather than restating it.

Tracking issue: **#1144**, now closed, which is itself a signal: the programme this plan opened with
is finished, and what remains is a different shape. Branch policy is unchanged, per #377: each pass
cuts its own branch from `main`'s tip and merges straight back, with two named exceptions recorded
under "Long-lived branches" below.

**Rewritten 2026-11-23, because 8.0.2 shipped.** OCCT tagged `V8_0_2` on 2026-11-21, and on
2026-10-30 the user had held v4.0.0 open until it did. So family E is now the critical path:
**v4.0.0 ships on `V8_0_2`**, with the carry policy below deciding what we add on top of it.

**Revised 2026-11-24: two kernel flavours.** The default kernel is **hardened** (`V8_0_2` plus the
carried patches). An opt-in **LTS** flavour is vanilla `V8_0_2` and, later, future upstream
releases. The release also stops being a long beta series: v4.0.0 goes straight to its release
candidate, and every tag after it is a plain release. Family E below carries the detail.

Two earlier rewrites shaped the rule that survived. On 2026-09-23 the 8.0.2 repin became the spine
because the release was confirmed for 25 September. On 2026-09-28 it was demoted to a conditional
because it had not shipped, and the plan had spent three days blocked on another project's calendar.
That lesson still holds for the next upstream release: plan on a tag, never on a date.

## Why this plan exists, and why it isn't optional

**v3.0.0 shipped 2026-08-18 without one.** It accumulated two breaking changes (#844, #943) and a
tail of Pass 2a/2b/3 dedup work, and got tagged when it was time to cut a release rather than from a
drawn scope line. That worked because it was small. It did not work again: the v4.0.0 line has
accumulated **fifteen** breaking changes across 196 merged pull requests, and the next release was
forced to be a major long before this paragraph was rewritten.

The complete register, with migrations, is [`SEMVER.md`](SEMVER.md)'s v4.0.0 section, assembled
2026-09-22. **Do not maintain a second copy of it here.** An earlier version of this document kept
a five-row MAJOR table that drifted immediately, and one of its five rows was wrong:

> [#1138](https://github.com/SecondMouseAU/OCCTSwift/pull/1138) claimed "14 more `SAWireAnalysis`
> functions return `Bool?`, not `Bool`". Its merged diff is nine lines of comment in
> `OCCTBridge_Healing.mm` plus a census document. It touches no header and no Swift file, and those
> fourteen functions return plain `Bool` today. The change was never made.

That was caught at release assembly, by checking each stated impact against the source rather than
against its PR body. Fourteen of fifteen held. Two further breaks (#1103, #1116) had been made by
PRs that declared nothing and were re-derived from their diffs. Both facts are recorded in
`SEMVER.md` rather than restated here.

## Scope

Families A, B and C are **complete**. What is live is D, E and F. **E is the critical path** since
2026-11-23. D and F continue on their own branches and do not gate the release.

### E. OCCT 8.0.2 (the critical path)

`V8_0_2` was tagged on 2026-11-21. **v4.0.0 ships on it.** The survey is done and recorded in
[`occt-upgrades.md`](occt-upgrades.md) under "8.0.1 to 8.0.2": no API or ABI break; of 61 carried
patches, ten retire, three rebase and 48 apply unchanged.

**The carry policy (decided 2026-11-23).** 8.0.2 is the floor, and where upstream chose a form for a
fix, we take their form. We carry a fix beyond 8.0.2 when it keeps a process alive or makes an
answer true, and every carried patch has an upstream pull request or issue before the release
candidate. What puts this package "too far out in front" of upstream is carrying what upstream
cannot see, not carrying safety. Of the 51 patches that remain:

| Group | Count | Note |
|---|---|---|
| Thread safety and races | 14 | Results-neutral. OCCT 8.1 removes the static state instead of locking it, so these retire at v5, and no new mutex-style fix is submitted |
| Damaged-input and checker hardening (`0069` to `0080`) | 12 | Results-neutral. Almost none is filed upstream yet |
| Modeling crash and hang guards | 13 | Results-neutral |
| Wrong-answer fixes | 11 | Nine have an upstream pull request open. `0057` is to file. `0028`'s contract differs from IR's #1620 only where no OCCTSwift call reaches |
| Behaviour ahead of upstream: `0059` | 1 | Kept (user decision), and submitted upstream |

Kernel patches added during v4.0.x must be results-neutral safety fixes, filed upstream issue first.
Where the bridge can guard a defect, guard it in the bridge (that protects both flavours) and patch
the kernel only when it cannot.

**Two kernel flavours (decided 2026-11-24).**

| Flavour | Kernel | Default | What it promises |
|---|---|---|---|
| **Hardened** | `V8_0_2` plus the 51 carried patches | Yes | The quality guarantee: no race the patches fix, damaged input refused, crash guards, and the 12 answer-changing fixes |
| **LTS** | `V8_0_2` exactly, then each upstream release | No, an explicit opt-in | A provenance guarantee: exactly what Open Cascade ships, so any defect is upstream's and upstream's support lineage applies |

LTS means provenance, not robustness. 39 of the 51 carried patches change no results (14
thread-safety, 12 damaged-input hardening, 13 crash and hang guards), and on a vanilla kernel they
become races and uncatchable crashes where the hardened kernel refuses or serialises. So LTS makes
no ThreadSanitizer-clean claim, is not safe for untrusted BREP, STEP or OCAF input, and has no
crash-guard promise. On wasm it still carries the 11 WASI port patches, because OCCT does not build
for wasm without them. The 12 answer-changing patches (11 wrong-answer fixes and `0059`) mean the
two flavours also give different results in places; the flavour contract is in
[`occt-upgrades.md`](occt-upgrades.md) and is generated from the ledger below once that exists.

**Mechanism: a package trait, behind a spike.** A default-off trait `UpstreamKernel` selects the
vanilla binary target. It is not assumed to work: Phase F's spike has pass and kill criteria (two
binary targets selected by a trait build and link under `swift build` and `xcodebuild`; the
unselected artifact is not downloaded; a root app can enable the trait and the whole graph flips;
the bridge compiles against both header sets). On a kill the fallback is a **version line**, never
a second repo: LTS is the 4.0.x lineage on its own branch and hardened is 4.1 and later, which
inverts the numbering and is why the trait is tried first. **LTS ships in v4.0.0 only if its exit
criteria are met by the release candidate; otherwise as v4.1.0** (adding a non-default trait is
additive). It never delays GA.

**What SwiftPM and the Swift Package Index do with this (verified 2026-11-24 against SE-0450, the
SwiftPM source and the SPI server source):**

- SwiftPM reads git tags only and ignores GitHub's "pre-release" flag. A version range includes
  pre-releases only if one of its bounds has a pre-release identifier, so `from: "4.0.0"` never
  resolves a `-beta`, `-rc` or `-kernel` tag. The exact pins in eight ecosystem repos exist because
  `-kernel` sorts above `-beta`; that ends at the RC (`-rc` sorts above `-kernel`) and after GA.
- SPI classifies a version by its semver tag (`semVer.isPreRelease`), and ignores non-semver tags.
  Set both the semver identifier and the GitHub flag; the flag still drives GitHub's "Latest"
  label and the release skill's `isPrerelease` check.
- A binary target's `url:` is independent of tags, so kernel assets go on non-semver tags
  (`kernel-8.0.2-c1` for the carry kernel, `kernel-8.0.2` for vanilla). That keeps the semver tag
  list and SPI's pre-release label clean; it is hygiene, not a prerequisite for `from:`.
- Traits unify as a union across the whole dependency graph, so any package can silently switch
  every consumer to the vanilla kernel, and SE-0450 says traits should be additive and that mutually
  exclusive ones should be avoided. `UpstreamKernel` removes safety and no API, so it is off that
  guidance but not forbidden. The mitigation is a gate in the ecosystem repo that fails if any
  library package under SecondMouseAU enables it: only root apps may. SPI builds default traits only,
  so what SPI compiles and documents is the hardened flavour.
- Not verified, so spike items: a `binaryTarget` as a trait-conditional dependency, whether the
  unselected 150 MB artifact is downloaded, and whether an Xcode app project can enable a trait.

**The kernel-fix ledger carries and retires the guards.** Today a retired guard is retired from
memory: [`known-occt-bugs.md`](../okf/references/known-occt-bugs.md) lists three that outlived their
fix because no test could say so. The ledger makes it mechanical and per flavour.

- **One row per defect** in `Scripts/kernel-fixes.tsv`: a stable fix id (`F0080`), the defect, the
  OCCT issue or PR, our patch number, the first upstream release containing a fix, the relation of
  upstream's fix to ours (`identical`, `same-code`, `different-form`, `different-behaviour`,
  `none`), and the guard and test sites.
- **Each kernel build emits `OCCTKernelFixes.h`** into the xcframework's Headers from the ledger:
  `OCCTSWIFT_KERNEL_FLAVOUR` and one `OCCTSWIFT_KERNEL_HAS_F0080` per fix present. Each flavour ships
  its own header, so the bridge sees the right macros with no trait-driven define.
- **A guard for a kernel defect** is wrapped `#if !OCCTSWIFT_KERNEL_HAS_F0080` and tagged
  `kernel-defect: F0080`. A test that needs the fix carries a `requiresKernelFix("F0080")` trait. A
  crash test cannot be a known issue (it kills the process), so on a kernel without the fix it is
  skipped.
- **Static gates:** every tag names a ledger row; the vanilla manifest lists zero patches; a row
  whose fix is present in every shipping flavour while a guard survives fails with "retire this
  guard".
- **Retirement is per flavour.** The carry flavour retires a guard at the repin that carries the
  patch. LTS retires it when vanilla OCCT reaches the release containing the fix, which for a fix
  upstream never backports to 8.0.x means v5. That is the recurring cost of an LTS flavour.
- **Reinstatement.** Guards retired at earlier repins come back for LTS from git history: the
  surface-less clause at the two Boolean-check sites (#3533), the analyzer guards (#3503), the datum
  lookup guard (#1030) and the bridge arc-length subdivision (#603).

**When upstream picks patches that are not ours.** 8.0.2 is the measured case: of 61 carried
patches, 13 (21%) were touched by upstream's own picks. Every future release will do the same.

| What upstream did | Action |
|---|---|
| Identical or same code as ours | Retire ours; the ledger row gains the release |
| A different form, same result | Retire ours, take upstream's, re-measure our suite |
| Different behaviour (`0054`: upstream refuses and throws where ours continued) | Take upstream's; the bridge adapts; mark the row `different-behaviour`, add a SEMVER row if an answer flips |
| Touched nearby, ours still needed | Rebase by three-way merge against the patched tree (`0053`, `0073`, `0074`) |
| Covers half of ours | Never carry only the surviving half: the half upstream took is what makes the other half safe. Keep ours whole, or drop it whole and file the gap |
| Someone else has an open PR for the same defect | Do not submit a duplicate: test theirs against our repro and carry ours until theirs lands |
| An IR-merged fix 8.0.x did not backport | Carry the whole PR only, as its own ledger row, retiring at the release that contains it |

`Scripts/survey-upstream-release.sh <tag>` (to be committed from the survey's scratch scripts) emits
this verdict table, so 8.0.3 or 8.1 is a run and not a day.

**Three rules the survey followed, each because it has already cost this project once:**

- **An absorbed patch is retired, not re-applied.** `Scripts/lib/apply-patches.sh` treats a patch
  that reverse-applies as already applied, so leaving one in place would not fail the build; the
  retirement is recorded, not inferred from a log. Patch `0032` shipped four days after upstream had
  fixed the same globals better (#1371, PR #1472).
- **Patches are authored against the patched tree, not the vanilla one.** `0073`, `0074` and `0076`
  are a stack. `0076` conflicted only because `0074` had not applied, and it needed no change.
- **The survey comes before any build.** A rebuild that starts first turns a patch conflict into a
  compile error several hundred files deep.

**Versioning.** 8.0.1 to 8.0.2 is an OCCT **patch**, so [`SEMVER.md`](SEMVER.md) Rule 1 (an OCCT
*major* bump) does not fire. What the move changes is behaviour, recorded per test in the repin
(#3536). The deprecations (#3538) are additive.

**No more betas.** `v4.0.0-beta.8` was not cut (user decision 2026-11-23): the `kernel.9` repin
(#3532) and the guard it retired (#3533) merged without a tag. **There is no beta.9 either**
(2026-11-24). The carry kernel is followed by the scope close-out and then `v4.0.0-rc.1`, and the
RC's `SEMVER.md` assembly starts from the drafted beta.8 text.

**Cadence after v4.0.0: no unending betas.**

- Every tag after GA is a plain release. There is no `-beta`, and no kernel asset in the semver tag
  namespace: kernel assets live on `kernel-8.0.2-c1` and `kernel-8.0.2`. The existing
  `v4.0.0-kernel.N` tags stay, and the scripts and gates that match that pattern are updated once.
- Pre-releases return only for a major OCCT jump (8.1 to v5), as `-rc.N` only, one cycle, exiting on
  the RC criteria below. A finding at the RC is `rc.2`, not a beta series.
- Patch releases (4.0.x) are proposed within about two weeks of an upstream tag, after the survey,
  and otherwise when a results-neutral fix is ready, at most monthly. A minor (4.1) is for additive
  API. A patch that is not ready is not in: the carry series is never a beta channel.
- The carry set is bounded and converges: every patch has an upstream issue or PR by the RC, a patch
  upstream has not touched across two upstream releases is reviewed to retire or escalate, and the
  count goes in every release note (61 to 51 at 8.0.2).

The three questions this section used to list as open to Phase 0 are answered, and the answers are
worth recording here because two of them were wrong in a way a plan should not repeat:

- **The file-path problem was not the largest remaining API question.** The path-taking STEP entry

- **There is no size budget, and setting one was the mistake.** #1689's 5 MB was withdrawn as

  exceeds it before any OCCT is in the module. #2761 holds the measurements and the untried levers
  and reports rather than grading. `wasm-feasibility.md` is the one place that discusses the
  withdrawn figure; nothing else should compare a measurement to it.
- **`wasm32-unknown-unknown`**, which #1689 requested, was neither of the two real targets. The
  branch name recorded the resolution: `wasm32-unknown-wasip1`.

**Phases 1 to 5 are not in v4.0.0**, and Phase 0 finishing does not change that.
`wasm-feasibility.md` costs them at weeks-to-months and calls this a porting project rather than a
recompile. The nine open follow-ups (#2048, #2052, #2269, #2272, #2757 through #2761) are the
inventory.

## The rule that keeps this from becoming "hold everything, forever"

**Every pass in this programme found more work mid-flight than it started with.** #396 spawned
#1071 spawned two more PRs. #928 spawned #930. Pass 4a's own closing comment has a section literally
titled "Added after this summary was first posted." That is not a criticism of any of those passes;
finding real, unscoped work is what an audit is for. It is why this section exists.

**A finding discovered while working an in-scope issue ships in v4.0.0 if it stays inside that
issue's own lane.** A finding that opens a materially new workstream gets filed and explicitly
deferred to whatever ships after v4.0.0.

The rule held under pressure during the beta.3 cut and is worth the example. Retiring the three
bridge-side mitigations the repin made obsolete (#1030, #603, #1515) surfaced that
`occtswift-wrapping-gaps.md` had recorded the datum point accessor as blocked by one of those
guards. Patch `0029` unblocks it, so wrapping it is now an ordinary job. It was **filed and not
done**, inside a PR that was already touching the file, because it is new surface rather than the
retirement's own lane.

8. **v4.0.0, then the ecosystem cascade** (#3540).

The LTS spike and flavour work (#3545) run in parallel with steps 4 to 6, and the upstream track
(#3541) runs alongside all of it. Neither gates the release.

1. Full `swift test` clean **across enough runs to cross the known ~1-in-10 parallel-suite flake
   rate**. One green run does not mean anything in this repo; #341/#344/#345's own history says so.
2. `Scripts/tsan-stress.sh all` clean, on the hardened flavour only: the 14 thread-safety patches

3. All **twelve** gates plus their `--self-test`s clean, the five censuses' `--self-test`s clean,

**SPI's handling of a prerelease is verified**, on 2026-09-23, after standing unverified for three
betas. The page shows `v3.0.0` as the latest release and `v4.0.0-beta.3` separately as the latest
beta release, which is the behaviour this plan wanted.

**The mechanism, corrected 2026-11-24.** An earlier version of this section said the `Pre-release`
flag on the GitHub release is what keeps a beta out of latest resolution. The sources say otherwise.
SwiftPM reads git tags and ignores that flag, and SPI classifies a version by whether its semver tag
carries a pre-release identifier. Every pre-release this repo published carried both, so the
observation above could not tell the two apart. What each one does:

| Signal | What reads it |
|---|---|
| The semver pre-release identifier in the tag (`-beta.N`, `-rc.N`) | SwiftPM (a range with no pre-release bound never resolves it), and SPI's release and pre-release labels |
| GitHub's `Pre-release` flag | GitHub's "Latest" label, and this repo's release skill (`isPrerelease`) |

So set **both**, and check the flag after publishing rather than trusting the tag name. A missing
`--prerelease` is still a release defect: a beta would take GitHub's latest slot.

```bash
gh release list --limit 5 --json tagName,isPrerelease,isLatest
```

The kernel pre-releases (`v4.0.0-kernel.1` and its successors) matter more than the betas: they
carry an `OCCT.xcframework.zip` asset that `Package.swift` pins, and are published in the middle of
a release window by design. Their asset URL is independent of any tag, which is why the carry and
vanilla kernels move to non-semver tags (`kernel-8.0.2-c1`, `kernel-8.0.2`) and leave the semver
namespace to the library.

## How the release is tracked

One milestone per pre-release (`v4.0.0-beta.1` through `.4`, then `v4.0.0-rc.1`; there is no
`beta.9`), since that is the granularity actually being decided. **Sub-issue links stay with each issue's real parent**, not the tracking issue: GitHub
allows one parent per issue, so something already under #377 or #807 cannot also link under #1144.

| Mechanism | What it expresses |
|---|---|
| **`v4.0.0-beta.N` milestones** | Which release chunk an issue ships in. The primary membership signal. |
| **Sub-issue links, on each issue's own natural parent** | Hierarchy/workstream, unchanged from #377/#807's trees. |
| **`release:v4.0.0` label** | Membership in this major, independent of which beta. |
| **`phase:*` labels** | Workstream. |
| **Board `Status`** | Backlog, In Progress, PR Review, Code-Review, Ready, Done. |

#1144, the tracking issue, is **closed**: the duplication and refman programmes it tracked are done.
E, D and F are tracked by their own issues and branches rather than by reopening it.

## Versioning

**Rule 2** of [`SEMVER.md`](SEMVER.md): accumulated breaking changes to the public Swift API.
Fifteen of them, registered with migrations in that file's v4.0.0 section.

**Rule 1 does not fire.** The kernel moves this release, from `V8_0_1` to `V8_0_2`, but that is an
OCCT *patch*. Rule 1 is about an OCCT *major*, which is what made v1.0.0 a major alongside OCCT
8.0.0 GA. A patch bump is a MINOR trigger at most and forces nothing, exactly as the
`v4.0.0-kernel.1` rebuild did. The previous version of this document said "the OCCT kernel is not
expected to move for this release (no OCCT 9.0 signal)", which conflated the two: there is still no
9.0 signal, and the kernel is still moving.

**`SEMVER.md` is assembled once, at release**, from each merged PR's own `## SemVer impact`
statement, per [`semver-at-release.md`](../okf/policies/semver-at-release.md). Do not hand-edit it
before then. The v4.0.0 section exists already because beta.3 needed it; it is re-assembled, not
appended to, when 8.0.2's own breaks are known.

Two things that assembly taught, both now written into that file rather than here: a stated impact
can describe a change that never landed, and a PR can make a break and declare nothing. Both
happened in this line, and both were caught only by checking claims against the source.
